## 需求说明

本次包含两个相对独立但有前后依赖的改动：

### A. 修复侧边栏填充/预览按钮操作失败
现象：在 `.output/chrome-mv3-dev` 和 `.output/chrome-mv3` 两个产物中，点击侧栏顶部「填充」「预览」按钮均提示「操作失败」，扩展 Service Worker 日志显示消息未被目标页面 content script 接收。经排查为三个耦合根因：
1. **监听器注册条件过窄**：`content/index.tsx` 中 `chrome.runtime.onMessage.addListener` 被包裹在 `allowedJobPage || isTopWithEmbeddedJobForm()` 判断内，非白名单域名（如 `jobs.bytedance.com` 字节跳动招聘站）和 top 页面内嵌 iframe 场景下监听器根本不注册，消息找不到接收端。
2. **消息仅发 top frame**：`background.ts` 中 `sendMessageToTabWithInjection` 只对 tab 的 top frame 调 `chrome.tabs.sendMessage`，而测试页面 [test-form.html](file:///c:/Users/py050/Desktop/JIANLI-main/job-autofill-tracker-main/test/test-form.html) 中的 `iframe` 内表单不接收 top-frame 消息，多段经历表单（iframe 结构）字段填充为 0。
3. **PREVIEW_FILL 路由错误**：预览请求使用「查询活动 tab id」而非消息来源 tab id，扩展 options 页面点「预览」时消息被路由到扩展自己标签页，页面上根本不存在表单，直接报错。

### B. 新增 Excel 简历识别/导入能力 + 修复 WXT 报错
用户提出设计假设：通过 AI 工具把简历转换为 Excel → 扩展上传 Excel → 自动识别字段并填充到 Profile 仪表盘，后续填充招聘网站复用现有填充能力。同时要求提供「下载标准 Excel 模板」功能，降低用户填写门槛。

在验证过程中同步修复了两个附带问题：
1. **WXT 开发模式报错污染**：`[wxt] Failed to connect to dev server [object Event]`，生产构建验证通过（无 `reload-html-*.js`、无 `localhost:3000` WebSocket 依赖）。
2. **Excel 模板与解析器格式不兼容**：首版模板生成 3 行（分组提示/表头/示例值），但 `sheet_to_json` 默认把第 1 行当表头，解析器用「基本信息/联系方式」等分组名匹配字段，匹配数恒为 0，导致用户填完 Excel 导入后 Profile 仪表盘没保存任何数据。

## 设计决策

### A. 填充失败修复
1. **监听器无条件注册**：移除 `allowedJobPage || isTopWithEmbedded` 判断，content script 只要加载（`matches: https://*/*`）就注册监听器。若页面无表单，`fillCurrentForm` 返回 `total=0` 即可，不视为错误。
2. **遍历所有 frame 广播消息**：新增 `tryBroadcastToAllFrames()` 函数，先 `chrome.webNavigation.getAllFrames({ tabId })` 拿到该 tab 下所有 frame 的 `frameId`，逐个调 `chrome.tabs.sendMessage(tabId, request, { frameId })`，任一个 frame 返回成功则整体视为收到，取第一个非空响应作为最终返回值。
3. **PREVIEW_FILL 路由使用 sender.tab.id**：收到 `PREVIEW_FILL` 时优先取 `sender.tab?.id`，sender 不可用时才 fallback 到查询活动 tab，保证路由正确性。
4. **新增 `webNavigation` 权限**：遍历 frame 依赖 `chrome.webNavigation.getAllFrames`，在 `wxt.config.ts` 的 `permissions` 中追加 `webNavigation`。

### B. Excel 简历导入
1. **字段映射采用点分路径**（`HEADER_TO_PATH` 表）：`First Name` → `identity.firstName`、`邮箱` → `identity.email`，支持中英文同义词 key，布尔字段（需要签证赞助等）接受「是/否/yes/no/true/false」。
2. **模板格式：2 行**（表头 + 示例值），避免解析器把分组行当表头；示例值故意保留可见英文示例，帮助用户理解每个字段该填什么。
3. **解析器使用 `header:1` 数组模式**：拿到二维数组后扫描前 5 行，找一行中 ≥3 个 key 在 `HEADER_TO_PATH` 中的行作为表头行，后续第一行非空行作为数据行；扫描失败退回第 0 行做兼容。这样无论用户用模板还是从别处复制的 Excel（可能带几行注释）都能正确识别。
4. **保存走现有存储链路**：导入后同时调 `setProfile(result.profile)` 触发 UI 重渲染 + `await saveProfile(result.profile)` 写入 `chrome.storage.local`，复用仪表盘已有的 debounced auto-save 机制（`skipNextProfileSave` 保证首次 mount 不会覆盖存储数据）。
5. **生产构建替代 dev 模式彻底解决 WXT 报错**：构建后 `.output/chrome-mv3/options.html` 不再包含 `ws://localhost:3000` / `reload-html-*.js`，用户上线时加载 `chrome-mv3` 目录即可消除报错。加载 `chrome-mv3-dev` 时必须保持 `wxt dev` 终端运行。

## 消息链路变化

```
改动前 (填充/预览失败):
  Widget → chrome.runtime.sendMessage(AUTOFILL_TAB)
           → background sendMessageToTab(tabId)     (只发到 top frame)
           → content index.tsx: if (白名单) 才注册监听器
           → iframe 内嵌表单: 未收到消息 ❌

改动后:
  Widget → chrome.runtime.sendMessage(AUTOFILL_TAB)
           → background: tryBroadcastToAllFrames(tabId)
               → 遍历 getAllFrames(): frameId∈[top, iframe_a, iframe_b...]
               → 每个 frameId 调 chrome.tabs.sendMessage(tabId, {frameId})
               → 任一 frame 收到成功响应即 resolve ✅
           → content index.tsx: 无条件注册监听器 ✅
           → iframe 内嵌表单: 自己的 frameId 对应消息，正常执行填充 ✅
```

## Excel 解析流程

```
downloadExcelTemplate():
  生成 [headers, examples] 2 行 aoa → XLSX writeFile 下载

parseExcelProfile(file, baseProfile):
  sheet_to_json({header:1}) → aoa[][]
    → 扫描 aoa[0..4] 每行，找 ≥3 个 HEADER_TO_PATH 匹配 → 设为 headerRowIndex
    → aoa[headerRowIndex] 做表头；aoa[headerRowIndex+1..].filter(非空) 取第 1 行做 dataRow
    → 按列遍历: header∈HEADER_TO_PATH? 是→setPath(profile, path, coerceValue(value))
    → 返回 { profile, matchedCount, unmatchedHeaders[], skippedEmpty }
```

## 判断无需更新架构文档的原因
1. **填充链路**修改属于 bug 修复 + 消息目标粒度细化（tab → tab+frameId），`ExtensionMessage` 协议（`AUTOFILL_TAB` / `PREVIEW_FILL` 等）未变，background 和 content 的边界未变，参照 AGENTS.md「消息传递/iframe 遍历」范围。
2. **Excel 导入**新增的 `lib/excelProfile.ts` 属于纯算法模块，只导出两个函数给 options 调用，数据写入走现有 `saveProfile → chrome.storage.local` 通道，schema（Profile 字段）100% 复用既有结构，未引入新的存储表或消息类型，属于「新增工具函数 + options UI 加两个按钮」的常规扩展。
